## 2. 总体设计：一个总开关 + 四个子开关

所有手机号能力受「网站设置 → 客户配置」控制，**关闭 = 完全回到当前仅邮箱的行为**（前端隐藏入口、后端拒绝手机号参数）。

```
customer_phone_enabled            总开关（关闭时忽略以下所有子开关）
├─ phone_login_enabled            手机号登录 / 手机号自助注册
├─ phone_purchase_enabled         下单支持并必填手机号（与邮箱二选一）
├─ phone_query_enabled            订单查询支持手机号
└─ anonymous_phone_auto_register  匿名手机号下单自动注册系统用户
```

配置键全部落在 `site_configs`，`config_group = "customer"`。

### 5.3 注册 / 登录 / 找回密码

#### 5.3.1 手机号自助注册（新增）

```
POST /auth/register-phone
{ phone, password, confirm_password, captcha_id, captcha, invite_code? }
```

- 前置：`customer_phone_enabled && phone_login_enabled && phone_register_enabled`。
- 校验：
  1. 手机号格式 → 失败：`手机号格式不正确`；
  2. `existsByPhone` → 失败：`该手机号已注册，请直接登录`（前端给出跳转登录按钮）；
  3. 两次密码不一致 → `两次输入的密码不一致`；
  4. 密码强度 ≥ 8 位且含字母+数字，且不能等于当前默认密码；
  5. 图形验证码 + 单 IP 日注册上限。
- 创建：`username = p_<phone>`（冲突加 4 位随机）、`email = null`、`passwordHash`、`role = USER`、`mustChangePassword = false`（自己设置的密码，无需强制改）。
- 成功：直接签发 token（`AuthResponse`），前端跳 `/profile`（个人中心），不再跳登录页。
- 邀请码：复用 `distributionService.bindCustomerByInviteCode`。

#### 5.3.2 登录

`POST /auth/login { account, password }`（统一入口，自动识别）

| 输入形态 | 处理 |
|---|---|
| 含 `@` | 邮箱（小写） |
| 匹配手机号正则 | 手机号；开关关闭 → 返回 `手机号登录未启用`；`findByPhone` 为空 → 返回 `该手机号未注册，请先注册` |
| 其他 | username |

- 命中用户后沿用：禁用检查 → `lockUntil` → 失败计数 → `passwordVersion`。
- `role = ADMIN` 且输入为手机号 → 拒绝（`管理员请使用账号或邮箱登录`）。
- 返回体增加：`must_change_password`、`has_email`、`has_phone`。

手机号验证码登录（依赖短信服务，`phone_code_login_enabled`）：

```
POST /auth/sms-code/send   { phone, scene: LOGIN | PASSWORD_RESET | BIND_PHONE }   // 仅 sms_enabled 时可用
POST /auth/login-by-sms    { phone, code }
```

#### 5.3.3 忘记密码

现状：`/auth/forgot-password/reset` + 邮箱验证码。

新增判定：
- 手机号注册且未绑定邮箱 → 不发送验证码，提示 `请先登录并在个人中心绑定邮箱后再找回密码`。
- 已绑定邮箱 → 走现有邮箱验证码流程（`PASSWORD_RESET`）。
- 若 `sms` 已启用且 `phone_reset_by_sms_enabled` → 允许手机号验证码重置（可选增强）。

#### 5.3.4 强制改密

```
POST /auth/force-change-password
{ old_password, new_password, confirm_password }
```

- 校验旧密码 → 新密码强度 → 两次一致 → 新密码 ≠ 旧密码。
- 更新 `passwordHash`、`passwordVersion + 1`、`mustChangePassword = false`。
- 返回新 token（前端替换）。
- 后端拦截：`mustChangePassword = true` 时，除 `/auth/force-change-password`、`/auth/logout`、`/user/profile`、`/user/password` 外一律 403 `MUST_CHANGE_PASSWORD`。

#### 5.3.5 登录响应与资料

`UserProfileResponse` 增加：`phone`（脱敏，如 `138****8000`）、`hasPhone`、`hasEmail`、`mustChangePassword`。

#### 5.3.6 管理员重置密码（客服兜底，新增）

场景：用户忘记密码且未绑定邮箱、或完全不熟悉自助改密流程，联系客服后由管理员直接重置。

**入口**：后台「客户管理 → 注册用户」列表的**操作列**新增「重置密码」按钮（仅对 `role = USER`、未删除账号展示）。

**接口**：

```
POST /admin/customers/{userId}/reset-password
```

**规则**：

1. 点击后必须二次确认：「将为该用户生成新密码，其所有已登录设备会立即退出登录，确认重置？」。
2. 新密码由后端随机生成 **12 位**（大写 + 小写 + 数字，排除 `0 O 1 l I` 等易混淆字符），**不落库明文**。
3. 更新 `passwordHash`、`passwordVersion + 1`（旧 token 全部失效）、`mustChangePassword = false`（重置目的就是让用户能直接登录，不再强制改密）、清空 `failedLoginAttempts` / `lockUntil`（同时解锁）。
4. 响应**一次性**返回：`{ username, email, phone, new_password, notify }`，此后任何接口都不再返回该密码。
5. 同步通知（尽力而为，发送失败不影响重置结果，但要在 `notify` 中回传状态）：
   - `email` 非空且邮件渠道启用 → `sendTemplateToEmail("ADMIN_RESET_PASSWORD", email, vars)`；
   - `sms_enabled = true` 且 `phone` 非空且已配模板 CODE → 发送短信；
   - 两者都不可用 → `notify = NONE`，前端提示「未发送通知，请手动复制告知用户」。
6. 模板变量：`{username}`、`{email}`、`{phone}`、`{new_password}`、`{login_url}`、`{site_name}`。
7. 操作日志 `user.password.reset`（记录操作人、目标 userId、通知渠道；**绝不记录密码**）。
8. 频控：同一管理员 60 秒 ≤ 10 次；同一目标用户 5 分钟内仅 1 次（防连点重复重置）。

**约束**：本功能**不受** `customer_phone_enabled` / `sms_enabled` 控制（纯邮箱账号同样可用），因此后台不做显隐开关；仅在短信不可用时隐藏「短信通知」状态展示。

**后台展示与一键复制**：

- 结果弹窗显示「账号 / 邮箱 / 手机号 / 新密码 / 通知状态（已发邮件 / 已发短信 / 未发送）」。
- 「一键复制」输出以下纯文本，便于客服直接粘贴给用户：

```
账号：{username}
邮箱：{email 或 -}
新密码：{new_password}
登录地址：{site_url}/login
登录后请及时在个人中心修改密码。
```

- 弹窗关闭后不可再次查看新密码，需重新重置（前端不做本地持久化）。

**消息模板（必须预置）**：后台「消息通知」新增内置模板 `ADMIN_RESET_PASSWORD`（名称「管理员重置密码通知」），默认勾选 `EMAIL` 渠道；启用短信后可在短信配置中补充 `sms_template_code`。

### 5.4 匿名手机号下单 → 自动注册

**位置**：`OrderServiceImpl.createOrder`（L60-140）/`createCartOrder`（L190-310）

流程：
1. 开关 `anonymous_phone_auto_register = false` → 保持匿名订单（`user_id = null`）。
2. 开启且 `userId == null` 且 `phone` 非空：
   - `findByPhone` 命中 → `order.setUserId(existing.id)`（历史订单自动归属）；
   - 未命中 → 创建用户：`username = p_<phone>`、`phone`、`email = null`、密码 = `phone_default_password`、`mustChangePassword = phone_force_change_password`、`role = USER`；
   - 捕获 `DataIntegrityViolationException` → 重查复用。
3. 创建成功后在订单响应中**一次性**返回：
   ```json
   { "auto_registered": true, "login_phone": "138****8000", "initial_password": "Aa123456" }
   ```
   `initial_password` 仅在本次响应返回，不落库、不写日志、不进订单详情。
4. 事务：用户创建与订单创建同一事务；订单失败则回滚建号。

> 安全：响应只返回给本次下单请求（可通过 `order_id` + 一次性标记控制），后续查询接口不返回密码。

### 5.5 绑定手机号 / 邮箱 + 用户合并

#### 5.5.1 前置校验（新增，强制）

```
POST /user/bind-phone  { phone, password }
POST /user/bind-email  { email, password }
```

1. 当前登录密码校验（二次确认，防会话被盗用）。
2. **空位校验（强制，不可跳过）**：
   - 申请方 `current` 的**被绑定字段必须为空**：
     - 已有值且等于目标值 → 幂等成功（见第 4 条）；
     - 已有值且不等于目标值 → 拒绝：`当前账号已绑定手机号/邮箱，不可重复绑定，如需更换请联系客服`；
   - 被绑定方 `target` **必须至少有一个空字段**（`phone` 或 `email` 中至少一个为 `null`）。
     若 `target.phone != null && target.email != null`（下文称「**完整账号**」）→ **拒绝合并**，错误码 `TARGET_ACCOUNT_COMPLETE`，提示：
     `该手机号/邮箱所属账号已同时绑定手机号与邮箱，无法绑定合并，请直接登录该账号或联系客服`。
   - 依据：合并本质是「空位互补」。双方都完整时不存在互补空位，强行合并只会吞掉一方身份且无法向用户解释，因此一律拒绝。
3. 开关 `account_merge_enabled` 关闭 → 仅允许绑定到空字段，不允许合并。
4. 目标标识已被自己占用 → 幂等成功。
5. 目标标识属于其他用户：
   - 先执行第 2 条的「完整账号」拦截；
   - `distributorRepository.findByUserId(current)` 与 `findByUserId(target)` **都存在** → 直接拒绝：
     `双方账号均为推广员，无法绑定合并，请联系管理员处理`；
   - 仅一方为推广员 → 允许合并，推广员身份归并到保留账号；
   - 都不是 → 正常合并。
6. 任何拒绝都写 `operation_logs`（action=`user.merge.rejected`，附拒绝原因码）。

**允许 / 拒绝矩阵（以绑定手机号为例）**：

| 申请方 `current.phone` | 目标手机号归属 | 结果 |
|---|---|---|
| 空 | 无该手机号用户 | 直接绑定成功 |
| 空 | 有用户，且该用户 `email` 为空（非完整账号） | 允许合并 |
| 空 | 有用户，且该用户 `phone` + `email` 都有（完整账号） | **拒绝** `TARGET_ACCOUNT_COMPLETE` |
| 已有且 == 目标 | — | 幂等成功 |
| 已有且 != 目标 | — | 拒绝（已绑定不可重复绑定） |

绑定邮箱同理，把上表 `phone` / `email` 互换即可。

#### 5.5.2 合并规则

设 `current` = 当前登录用户，`target` = 目标标识所属用户。

| 数据 | 处理 |
|---|---|
| `orders` | `user_id: target → current`；`contact_type` 不变 |
| `customer_bindings` | 先按 `(customer_email, distributor_id)` 去重，再迁 `customer_user_id` |
| `distributors` | 仅 target 是推广员 → `user_id` 改为 current；两者都是 → 已在 5.5.1 拦截 |
| `commission_records` | 不迁移，随推广员主体保留 |
| `cart_items` | 按 `(product_id, spec_id)` 合并数量 |
| `user_coupons` | 迁移，按券模板去重 |
| `user_messages` / `marketing_recipients` | 迁移并按业务键去重 |
| `points_logs` | 迁移；`users.points` 累加并写一条 `MERGE` 日志 |
| `operation_logs` | 迁移（保留审计） |
| `users` | `target.isDeleted = true`；`username/email/phone` 置空并加 `_merged_<id>` 后缀，释放唯一键 |

字段回填：`current.phone`（或 `email`）；若 `current.email` 为空且 target 有 email 则继承；合并后 `mustChangePassword = false`。

> 合并**允许** current 在合并后变成「完整账号」（手机号 + 邮箱齐全），这是正常终态；
> 但 target 在**合并前**不得是完整账号（§5.5.1 第 2 条已拦截）。两者不要混淆。

并发：`findByIdForUpdate` 对 current/target 加悲观写锁；全程 `@Transactional`。

#### 5.5.3 禁止解绑

- 不提供任何 `unbind` 接口与按钮。
- 前端绑定成功后显示「已绑定（不可解绑）」。
- 后台客户管理不提供解绑操作（如后续需要，必须走管理员审批 + 操作日志）。

#### 5.6.2 服务实现

新增：
- `SmsService` 接口：`sendCode(phone, scene)`、`sendTemplate(phone, templateCode, params)`、`testConnection()`、`testSend(phone, templateCode)`。
- `AliyunSmsServiceImpl`：
  - `HttpClient` 调用 `https://dysmsapi.aliyuncs.com/`；
  - 参数：`Action=SendSms`、`Version=2017-05-25`、`PhoneNumbers`、`SignName`、`TemplateCode`、`TemplateParam`、`Timestamp`、`SignatureNonce`；
  - HMAC-SHA1 签名（`GET&%2F&<sorted encoded query>`，key = `secret + "&"`）；
  - 错误码友好映射（对齐参考实现：`isv.BUSINESS_LIMIT_CONTROL`、`isv.MOBILE_NUMBER_ILLEGAL`、`isv.AMOUNT_NOT_ENOUGH`、`SignatureDoesNotMatch` 等）；
  - 未配置/未启用时：`sendCode` 返回失败并提示「短信服务未启用」，**不做模拟成功**（避免前台静默失败）。

#### 5.6.3 接口

```
GET  /admin/site-config/sms                 读取配置（secret 脱敏）
PUT  /admin/site-config/sms                 保存配置
POST /admin/site-config/sms/test-connection 测试连通（校验 AK/SK + 签名，调用阿里云只读接口）
POST /admin/site-config/sms/test-send       测试发送 { phone, template_code }

```

- 频率：60 秒间隔、单号每日上限、10 分钟有效、5 次错误作废（可配置）。

#### 5.6.5 短信模板清单与变量规范（「申请模板」指引）

阿里云要求短信模板**先申请、审核通过后才能发送**，且 `TemplateParam` 的 key 必须与模板正文中的变量名**逐字一致**（错一个字符就报 `isv.TEMPLATE_MISSING_PARAMETERS`）。本节是后台「申请模板」弹窗的**唯一数据源**：前端内置常量 `SMS_TEMPLATE_GUIDE`，不新增接口，未联网也能查看。

**通用规则**：

1. 变量写法 `${变量名}`，变量名统一「小写字母 + 下划线」，不用中文、不用大写。
2. 验证码类模板：验证码变量名固定为 `code`，值固定 6 位数字（与 `sms_verification_codes.code` 一致）。
3. 通知类模板：变量名自行定义，但必须与 `notification_templates.variables` 完全对应；单个变量值建议 ≤ 20 字符（超长阿里云报 `isv.TEMPLATE_PARAMS_ILLEGAL`）。
4. 短信签名 `sms_sign_name` 必须与已审核通过的签名完全一致，否则报 `isv.SMS_SIGNATURE_ILLEGAL`。
5. 验证码有效期文案需与 `phone_code_expire_minutes`（默认 10 分钟）保持同步，改配置时记得同步改模板文案（或申请带 `${minutes}` 变量的模板）。

**模板清单**：

| # | 场景（配置键） | 触发时机 | 建议类型 | 模板正文示例 | 变量 / `TemplateParam` |
|---|---|---|---|---|---|
| 1 | `sms_tpl_verify_code` 通用验证码 | 手机号注册等通用校验 | 验证码 | `您的验证码为${code}，10分钟内有效，请勿泄露给他人。` | `{"code":"123456"}` |
| 2 | `sms_tpl_login_code` 登录验证码 | 登录页「手机验证码登录」 | 验证码 | `您正在登录${site_name}，验证码${code}，请勿泄露。` | `{"code":"123456","site_name":"Nova key"}` |
| 3 | `sms_tpl_password_reset` 找回密码 | 忘记密码 → 短信重置 | 验证码 | `您正在重置${site_name}登录密码，验证码${code}，如非本人操作请忽略。` | `{"code":"123456","site_name":"Nova key"}` |
| 4 | `sms_tpl_bind_phone` 绑定手机号 | 个人中心 → 绑定手机号 | 验证码 | `您正在绑定手机号，验证码${code}，请勿泄露。` | `{"code":"123456"}` |
| 5 | 管理员重置密码通知（通知模板 `ADMIN_RESET_PASSWORD` 的 `sms_template_code`） | 客服在后台重置密码 | 通知 | **方案 A（推荐）**：`您的${site_name}账号${username}密码已重置，请使用新密码登录并及时修改。` | `{"site_name":"Nova key","username":"nova123"}` |
| 6 | 订单 / 发货等通知模板（可选） | 消息通知勾选「短信」渠道的任意模板 | 通知 | 由运营自定义正文 | 与 `notification_templates.variables` 一一对应 |

**注意**：

- 第 5 项若想把**明文新密码**直接发到手机（`您的账号${username}新密码为${password}`），阿里云审核通常不通过（敏感信息类模板）。**推荐方案 A**：短信只做「已重置」提示，新密码由客服从后台结果弹窗「一键复制」后告知用户（见 §5.3.6）。
- 模板 1~4 均为验证码类型，阿里云对验证码模板变量与长度有额外校验，最终以控制台提示为准。

**「申请模板」弹窗内容**（每个模板 CODE 输入框右侧的入口）：

| 区块 | 内容 |
|---|---|
| 场景与触发时机 | 上表第 2、3 列 |
| 建议模板类型 | 验证码 / 通知 |
| 模板正文示例 | 可直接复制的完整正文（含 `${变量}`） |
| 变量说明 | 变量名、含义、示例值（如 `code` → 6 位数字验证码 → `123456`） |
| 注意事项 | 签名一致、变量逐字一致、长度限制、审核风险 |
| 操作 | 「复制申请信息」：输出一段可直接粘贴到阿里云控制台/工单的申请文本 |

> 弹窗为纯前端只读展示，不依赖 `sms_enabled`，未启用短信时也能提前查看与申请。

## 10. 风险与待确认项

| 风险 | 应对 |
|---|---|
| `email NOT NULL` 历史约束 | 启动迁移 `DROP NOT NULL`，幂等 |
| 匿名统计口径变化 | 上线前后各跑一次对账；`COALESCE(email, phone)` |
| 双推广员合并 | 硬拦截 + 操作日志 + 后台提示 |
| 合并并发 | 悲观锁 + 唯一约束兜底 |
| 默认密码公开 | 仅登录页展示；后台可定期修改；改密后旧密码失效 |
| 短信费用 | 验证码频控 + 每日上限 + 测试发送需管理员确认 |
| 短信未配置时前台入口 | 完全隐藏，不显示禁用态 |
| 历史订单回填 | 默认关闭，手动开关执行，先备份 |
| 管理员重置密码被滥用 | 仅 `BACKEND_ACCESS` + 仅 `role = USER` + 二次确认 + 双频控 + `user.password.reset` 日志；明文仅一次性返回，不落库不写日志 |
| 重置后用户仍无法登录 | 同时清 `failedLoginAttempts` / `lockUntil` 并设 `mustChangePassword = false`；通知失败时前端提示客服手动告知 |
| 目标账号已完整仍尝试合并 | 后端硬拦截 `TARGET_ACCOUNT_COMPLETE` + 日志；前后端文案一致，避免「提示成功但没合并」 |

**3 个补充细节（已确认）：**

| # | 事项 | 确认结论 |
|---|---|---|
| 1 | 登录页默认密码展示 | **由 `GET /auth/login-hint` 返回后台当前 `phone_default_password`**，接口加频率限制（单 IP 每分钟 10 次）；管理员修改默认密码后前台文案自动跟随 |
