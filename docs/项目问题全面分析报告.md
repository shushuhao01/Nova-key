# 项目问题全面分析报告

> 分析范围：`orion-key-main` 全项目（后端 Spring Boot 3.4 / Java 22，前端 Next.js 16 / React 19，PostgreSQL）
> 分析日期：2026-08-13
> 方法：静态代码走查 + 交叉核对实体/Repository/Service/Controller/前端页面与配置

---

## 一、结论摘要

| 严重程度 | 数量 | 核心风险 |
|---|---|---|
| 高危（P0/P1） | 7 | 明文密码、弱 JWT 密钥、支付页信任客户端参数、微信转账回调中间态误判、回调失败吞重试、佣金并发重复入账、微信绑定可劫持收款 |
| 中危（P2） | 18 | 前端 Token 存储与鉴权、XSS、mock 假成功、订单状态无锁、对账公式错误、N+1、异常处理缺失等 |
| 低危（P3）/优化 | 若干 | 日志泄露、无超时、轮询无退避、硬编码域名等 |

**最应优先处理的三件事：**
1. 生产配置必须显式覆盖 `JWT_SECRET`、`PASSWORD_PLAIN=false`、`DB_PASSWORD`、`MAIL_PASSWORD`（当前默认值可直接被利用）。
2. 支付页 `wallet/crypto_amount/qr/payurl` 不得信任 URL query 参数，收款地址/金额必须从服务端可信接口按 `orderId` 重新拉取。
3. 微信转账回调对 `PROCESSING/ACCEPTED` 等中间态的处理必须修正，避免冻结余额被提前退回导致重复打款。

## 二、高危问题（需尽快修复）

### H1. 默认明文密码存储（生产未配置时用户密码不加密）

- 位置：`apps/api/src/main/resources/application.yml:59` 与 `apps/api/src/main/java/com/orionkey/config/SecurityConfig.java:27-34`
- 描述：`application.yml` 中 `security.password-plain: ${PASSWORD_PLAIN:true}` 默认值为 `true`，即**默认使用明文密码**（`NoOpPasswordEncoder`）。`SecurityConfig` 中 `@Value("${security.password-plain:false}")` 的默认值 `false` 会被 yml 覆盖，实际生效默认仍是 `true`。
- 影响：若生产环境未显式设置 `PASSWORD_PLAIN=false`，所有用户密码（含管理员）以明文写入数据库，一旦数据库泄露即可直接登录。
- 建议：将 yml 默认值改为 `false`（BCrypt），并在部署环境变量强制 `PASSWORD_PLAIN=false`；对存量明文密码做迁移。

### H2. 默认弱 JWT 密钥（生产未配置时可伪造 token 提权）

- 位置：`apps/api/src/main/resources/application.yml:54`、`apps/api/src/main/java/com/orionkey/utils/JwtUtils.java:22`
- 描述：`jwt.secret: ${JWT_SECRET:nova-key-dev-secret-key-must-be-at-least-256-bits-long-for-hs256}` 仓库内置了已知默认密钥。
- 影响：生产未注入 `JWT_SECRET` 时，任何人可用该密钥签发任意 `role=ADMIN` / 任意 `userId` 的 token，完全接管系统。
- 建议：生产强制注入随机强密钥；启动时校验 `jwt.secret` 不等于该默认值（或直接移除默认值改为必填）。

### H3. 支付页信任 URL 查询参数（USDT 收款地址/金额可被篡改）

- 位置：`apps/web/app/(store)/pay/[orderId]/page.tsx:64-79`、`:331`、`:350`、`:370-372`
- 描述：收款地址 `wallet`、转账金额 `crypto_amount`、链 `chain`、二维码 `qr`、H5 链接 `payurl` 全部直接来自 `useSearchParams()`，且 `orderApi.getStatus(orderId)` 只返回 `payment_url`，并不返回/校验钱包地址与金额。
- 影响：攻击者可构造 `/pay/{真实订单号}?method=usdt_trc20&wallet=攻击者地址&crypto_amount=0.01` 诱导用户向攻击者地址转账，或展示错误金额。属于资金重定向级别问题。
- 建议：支付页只接收 `orderId`，所有支付参数（收款地址、金额、二维码、H5 链接）必须通过服务端接口按订单号重新获取并校验归属，禁止从 query 透传。

### H4. 微信转账回调把中间态（PROCESSING/ACCEPTED）当失败处理，冻结余额被提前退回

- 位置：`apps/api/src/main/java/com/orionkey/service/impl/DistributionServiceImpl.java:2594-2651`（`handleTransferCallback`）
- 描述：只有 `FINISHED`/`SUCCESS` 走成功分支，其余所有状态（包括 `ACCEPTED` 受理、`PROCESSING` 处理中）一律走失败分支：`frozen_balance` 扣回、`available_balance` 加回、提现单置 `FAILED`。而 `FAILED` 为终态，后续真正的 `FINISHED` 回调会在 `:2583-2586` 的幂等检查被直接丢弃。
- 影响：分销员在转账"处理中"就拿回了可提现余额，可再次发起提现；同时原转账随后真正到账 → 重复打款 / 资金损失。
- 建议：中间态（ACCEPTED/PROCESSING）只记录、保持 `PROCESSING` 不变，仅在明确的成功终态或失败终态（CLOSED/FAILED）才做余额流转；并增加主动查单对账。

### H5. 回调"查询状态不匹配"等可重试失败被写入幂等表，重试被吞导致已付款订单无法入账

- 位置：`apps/api/src/main/java/com/orionkey/service/impl/WebhookServiceImpl.java`（微信 `:386-389` / `:428-433`，支付宝 `:492-496` / `:542-556`，易支付 `:72-76` / `:151-168`，BEpusdt `:219-223` / `:304-320`）
- 描述：各渠道入口先做幂等检查（`findByEventId` 存在即返回成功应答）。但"服务端二次查单结果不匹配/查询失败"这类**可能是瞬态**的失败分支，会先 `saveWebhookEvent(...)` 写入幂等表再返回 `FAIL`。当网关按同一事件 ID 重试时，命中幂等检查直接返回成功应答，订单永远不被标记 `PAID`。
- 影响：典型场景是"网关查单接口最终一致、回调先到"，首次回调被 `QUERY_STATUS_MISMATCH` 误判并落幂等表，之后真实重试再也进不来。USDT 无主动查单兜底，影响最严重。
- 建议：仅对"已最终判定"的结果写幂等表；查询失败/查询不一致等可重试分支应直接 `return FAIL` 而不落幂等表。

### H6. 佣金入账幂等无锁且无唯一约束，并发回调可重复计佣

- 位置：`apps/api/src/main/java/com/orionkey/service/impl/DistributionServiceImpl.java:2238`（`findByOrderId(orderId).isEmpty()` 判重）、`apps/api/src/main/java/com/orionkey/entity/CommissionRecord.java`（整表无 `order_id/order_item_id/distributor_id` 唯一约束）
- 描述：`onOrderPaid` 的幂等是"先查后写"，`commission_records` 无唯一约束兜底。该入口有多个调用点（webhook 回调、主动查单、管理员确认、USDT 链上校验等）。
- 影响：同一订单被"回调 + 主动查单"并发命中时，两个事务都可能通过空检查，各自插入佣金记录 → 重复计佣。
- 建议：给 `commission_records` 增加 `(order_id, order_item_id, distributor_id)` 唯一约束作为最终兜底；订单 `PAID` 流转改用条件更新（`UPDATE ... WHERE status='PENDING'`）或悲观行锁。

### H7. 微信绑定回调 state 可预测、无签名、无身份校验，可劫持他人分销员收款

- 位置：`apps/api/src/main/java/com/orionkey/service/impl/DistributionServiceImpl.java:1528`（`state = d.getId()`）、`:1543-1566`（用 `state` 直接查分销员并写 openid）、`apps/api/src/main/java/com/orionkey/config/SecurityConfig.java:70`（该回调 `permitAll`）
- 描述：`state` 直接用分销员 UUID（可被公开接口如 `/distribution/resolve/{linkCode}` 枚举），无 HMAC 签名、无"当前登录用户 == 该分销员"校验、无一次性 nonce。
- 影响：攻击者拿到他人分销员 UUID 后，用自己的微信完成授权回调，即可把自己的 openid 绑定到受害者分销员，后续提现资金转入攻击者微信。资金重定向级别。
- 建议：`state` 改用带签名/过期的一次性 token，回调时校验签名、过期时间、且当前登录用户必须等于该分销员。

## 三、中危问题（建议尽快处理）

### M1. 前端 JWT/用户信息存 localStorage，可被 XSS 窃取
- 位置：`apps/web/services/api.ts:73-84`、`109-120`、`94-95`
- 影响：任何一处 XSS（本项目后台确有 `dangerouslySetInnerHTML`，见 M5/M6）都可读出 token 冒用管理员身份。
- 建议：改用 httpOnly Cookie（或至少短时效 token + 服务端会话）；修复所有 XSS 点。

### M2. 前端鉴权可被伪造绕过（无服务端路由守卫 / middleware）
- 位置：`apps/web/lib/context.tsx:306-325`、`apps/web/lib/hooks.ts:31-54`、`apps/web/components/layout/admin-shell.tsx:6-13`（全项目无 `middleware.ts`）
- 影响：后台外壳权限判断依赖 `localStorage` 里的 `user` 对象，可手动写 `{"role":"ADMIN"}` 绕过前端门禁。数据仍由后端校验，但属纵深防御缺失。
- 建议：增加服务端路由守卫或 `middleware.ts`；前端仅做展示，不作为安全边界。

### M3. 生产网络失败回退 mock 数据造成"假成功"
- 位置：`apps/web/services/api.ts:313-327`（`withMockFallback`）、`apps/web/lib/mock-data.ts:620-626`
- 影响：`login/register/order.create/cart/site config` 等关键路径在 fetch 失败时返回 mock 结果，生产环境后端宕机时用户看到"登录成功/下单成功"的假数据。
- 建议：mock 回退仅在 `process.env.NODE_ENV === 'development'` 下启用，生产直接抛错。

### M4. 支付渠道私钥明文返回前端
- 位置：`apps/web/services/api.ts:775-777`（`adminPaymentApi.getRawConfig`）
- 影响：管理员会话一旦被窃取即泄露支付私钥。
- 建议：后端脱敏返回（仅返回末 4 位），或二次鉴权后再返回完整密钥。

### M5. 邮件正文 `dangerouslySetInnerHTML` 未消毒（存储型 XSS）
- 位置：`apps/web/app/admin/marketing/page.tsx:1113-1119`、`:1178-1187`
- 影响：后端存储的邮件 HTML 直接注入 DOM，无 DOMPurify 消毒，低权限 STAFF 或被注入内容可触发存储型 XSS。
- 建议：注入前用 DOMPurify 消毒。

### M6. JSON-LD 注入存在 `</script>` XSS 隐患
- 位置：`apps/web/app/(store)/page.tsx:31-43`、`apps/web/app/(store)/product/[id]/page.tsx:64-89`
- 影响：`JSON.stringify` 不转义 `</script>`，若站点名/商品标题/描述等后端可编辑字段含 `</script><script>...` 即 XSS。
- 建议：对注入内容转义 `<` `>`（或 `</` → `<\/`）。

### M7. 二维码生成接口无鉴权、无限流、任意 URL
- 位置：`apps/web/app/qr-image/route.ts:14-39`
- 影响：可生成指向任意地址（含钓鱼地址）的二维码，挂在本站域名下放大钓鱼；也是 CPU DoS 向量。`size` 已被钳制到 120-800（此点正确）。
- 建议：增加协议白名单（仅 http/https）、速率限制、可选鉴权。

### M8. `typescript.ignoreBuildErrors: true` 掩盖类型错误
- 位置：`apps/web/next.config.mjs:16-18`
- 影响：类型不匹配在生产静默上线，掩盖潜在运行时错误。
- 建议：先修复存量类型错误再关闭该开关。

### M9. 订单 `PAID` 状态流转为"读改写"无锁（回调/主动查单竞态）
- 位置：`apps/api/src/main/java/com/orionkey/service/impl/PaymentServiceImpl.java:534-550`（`markPaid`）、`WebhookServiceImpl.java:180-191 / 324-337 / 436-448 / 563-575`
- 影响：回调与主动查单并发时可能都读到 `PENDING` 并通过，订单本身不会双入账（金额相同），但佣金/通知可能重复（见 H6）。
- 建议：订单 PAID 流转改用 `@Modifying UPDATE ... WHERE status='PENDING'` 或悲观行锁。

### M10. `onOrderPaid` 吞异常导致事务不回滚，可能产生"部分计佣"中间态
- 位置：`apps/api/src/main/java/com/orionkey/service/impl/DistributionServiceImpl.java:2427-2429`
- 影响：方法级 `catch (Exception) { log.error(...) }` 不重抛，`@Transactional` 不会回滚；若遍历订单项中途抛异常，前面已 save 的佣金记录会随事务提交，剩余订单项佣金丢失且无补偿。
- 建议：业务异常外，运行时异常应重抛触发回滚，或逐订单项独立事务 + 失败重试/告警。

### M11. USDT webhook 路径跳过链上确认数校验
- 位置：`apps/api/src/main/java/com/orionkey/service/impl/TxidVerifyServiceImpl.java:404-461`（`verifyForWebhook` 调 `queryTransaction(chain, txid, false)`），TRC20 `:259-262`、BEP20 `:325-326`
- 影响：webhook 路径可能接受仅 0~1 个区块确认、后续可能被链重组回滚的 USDT 交易。人工提交 TXID 路径做了确认数校验，两者不对称。
- 建议：webhook 路径同样启用确认数校验，或约定回调必须满足最低确认数。

### M12. 分销对账公式错误，必然误报
- 位置：`apps/api/src/main/java/com/orionkey/scheduler/DistributionScheduler.java:102-114`
- 影响：`expectedAvailable = SUM(SETTLED佣金) - withdrawnAmount` 未计入"提现中/被拒/取消"带来的余额变化，凡有此类记录的分销员都会被误报为"余额异常"，对账告警失真。
- 建议：重新推导余额公式，把 WITHDRAWING/REJECTED/CANCELLED 的余额影响纳入。

### M13. 提现超时/回调无行锁并发 + 超时不回查微信真实状态
- 位置：`apps/api/src/main/java/com/orionkey/scheduler/DistributionScheduler.java:66-80`、`DistributionServiceImpl.java:2588-2599`
- 影响：两条路径都读-改-写 `frozen_balance/available_balance` 且无行锁；超时只按时间判定、不回查微信侧转账真实状态，若微信已打款但回调丢失，会把已打款金额退回 → 重复发放。
- 建议：分销员行加悲观锁；超时处理前主动查微信转账状态。

### M14. `findActiveBindingByEmail` 可能命中多行，异常被吞导致整单佣金静默丢失
- 位置：`apps/api/src/main/java/com/orionkey/repository/CustomerBindingRepository.java:14-16`、`DistributionServiceImpl.java:2261`
- 影响：唯一约束是 `(customer_email, distributor_id)`，同一邮箱可绑定多个分销员；`findActiveBindingByEmail` 无 `LIMIT 1`，多行时 Spring Data 抛 `IncorrectResultSizeDataAccessException`，又被 M10 的 `catch(Exception)` 吞掉 → 该订单佣金整体不生成且无感知。
- 建议：改为 `findFirst...OrderByCreatedAtDesc` 或显式 `LIMIT 1`。

### M15. 商品列表/详情明显 N+1
- 位置：`apps/api/src/main/java/com/orionkey/service/impl/ProductServiceImpl.java:49`、`:263-288`、`:90-94`
- 影响：每个商品逐项查 specs、逐规格查库存、逐商品查销量，首页一页 20 商品即几十到上百次查询，是最重的 N+1 热点。
- 建议：用 `GROUP BY product_id` 批量聚合销量与库存。

### M16. 幂等键并发插入唯一约束冲突未处理
- 位置：`apps/api/src/main/java/com/orionkey/service/impl/OrderServiceImpl.java:52-65`、`:173-185`
- 影响：相同 `idempotency_key` 并发请求可能都查到"不存在"并各自插入，其中一个撞唯一约束抛 `DataIntegrityViolationException`，返回 500 而非已有订单。
- 建议：捕获唯一约束冲突并返回已存在订单。

### M17. 全局异常处理缺失 `DataIntegrityViolationException` 等，业务冲突变 500
- 位置：`apps/api/src/main/java/com/orionkey/exception/GlobalExceptionHandler.java:21-54`
- 影响：幂等键冲突、卡密重复、请求体 JSON 解析失败等落到兜底 `Exception` 返回 500，前端拿不到可读原因。
- 建议：显式捕获 `DataIntegrityViolationException`（映射 409/重复提交）、`HttpMessageNotReadableException`（400）。

### M18. 后台订单搜索 `str(o.id) LIKE` 无法走索引
- 位置：`apps/api/src/main/java/com/orionkey/repository/OrderRepository.java:192-206`（`:198`）
- 影响：`str()` 把 UUID 转字符串再 LIKE，无法使用主键索引，订单量大后按订单号搜索全表扫描。
- 建议：订单号搜索改为精确匹配或前缀索引方案。
